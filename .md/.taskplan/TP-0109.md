# TP-0109 — CI: ensaio de migration sobre dados e checagem aditiva [BD]

Reserva: Livre
ID no TASK.md: TP-0109 · Lote: Lote 21 · Agente: executor · Chapéu: Backend (operação) · Est: 4h · Dep: TP-0018, TP-0088 · Status no TASK.md: Pendente
Reqs: ADR-011 §4.2-4.3; RT-06, RT-14 · Aceite: Job que aplica as migrations da `main`, carrega o seed de volume (TP-0088) e então aplica as migrations novas do PR; passo que falha se uma migration nova tiver `drop`, `rename` ou `alter … type` sem um arquivo de justificativa ao lado; prova com uma migration de teste que adiciona `not null` sem default (o job falha)

## 1. Plano de execução
**Reaproveitamento:** USAR `.github/workflows/ci.yml` (TP-0007/TP-0018: acrescentar um job, não criar workflow), a preparação de pnpm (`.github/actions/preparar-pnpm/`) e a subida do Supabase local extraída no TP-0018 (`pnpm local:ci` ou composite action); `backend/supabase/volume/carregar.sh` (TP-0088) para o seed de volume, com a trava de host local dele (se for trecho inline, extrair para `backend/operacao/comum/host-local.sh` e usar nos dois); `backend/operacao/comum/testes/simular.sh` (TP-0008) nos testes de shell; passo `shellcheck backend/operacao/**/*.sh` (TP-0008) já cobre os scripts novos; lista de jobs exigidos do `migrar.sh` (TP-0008).
**Camada:** operação/CI: `backend/operacao/deploy/` (`ensaiar-migration.sh`, `checar-aditiva.sh`, `testes/`), fixtures SQL em `backend/supabase/ensaio/` (fora de `tests/` para o `supabase test db` não executá-las; G-08 exige SQL só em `backend/supabase/`).
**Referência visual:** não se aplica.

1. TDD: `testes/checar-aditiva.test.sh` (bash puro) → `checar-aditiva.sh` → `testes/ensaiar-migration.test.sh` [BD] → `ensaiar-migration.sh` → job.
2. Base de comparação: PR = `origin/$GITHUB_BASE_REF`; push na `main` = `github.event.before`; checkout com `fetch-depth: 0`. Migrations novas = `git diff --name-only --diff-filter=A <base>...HEAD -- 'backend/supabase/migrations/*.sql'`. Nenhuma nova → os dois passos registram "nenhuma migration nova" e passam.
3. `checar-aditiva.sh <base>`: em cada migration nova, sem os comentários `--` e `/* */`, procura (sem caixa) `\bdrop\b`, `\brename\b` e troca de tipo de coluna (`alter … alter [column] x [set data] type`); `alter type … add value` é aditivo e passa. Achou → exige `<nome>.justificativa.md` ao lado (mesmo nome, em `backend/supabase/migrations/`; conferir se a CLI da versão fixada ignora o `.md` ali; se recusar, usar `backend/supabase/migrations-justificativas/<nome>.md` e registrar).
4. **G-12 (regra ajustada pelo Gestor, Log de 2026-10-09, ressalva R3):** a justificativa só vale se citar (a) `Fase expand: <arquivo>` = migration que existe na `<base>` e foi adicionada à `main` há 30 dias ou mais (`git log <base> --diff-filter=A --format=%cs -1 -- <arquivo>`; a data de publicação em produção não é visível ao CI: registrar a aproximação no README), ou (b) `Exceção: <data>` de uma linha do Log de Alterações do `.md/GUARDRAILS.md` **lido da `<base>`** (`git show <base>:.md/GUARDRAILS.md`), que cite `G-12` e o nome da migration, com Validade "permanente" ou data não vencida. Linha de log acrescentada no próprio PR não conta (fecha a autoexceção). Fora disso: falha com a regra e o motivo na mensagem.
5. `ensaiar-migration.sh --base <ref> [--workdir-pr backend]`: trava de host local; `git archive <base> backend/supabase | tar -x -C <tmp>` (não mexe na árvore de trabalho); `supabase db reset --workdir <tmp>/backend` (migrations e seeds da `main`, mesmo `project_id`, mesmos containers; conferir na versão da CLI e registrar a alternativa se precisar); `carregar.sh` da versão da `<base>` (seed de volume com as funções que a `main` tem); `supabase migration up --local --workdir <workdir-pr>` aplica só as pendentes (as novas). Qualquer erro → código ≠ 0 com o erro do Postgres no log.
6. Job `migration` em `ci.yml`: em push e PR, sem `if:`/`continue-on-error`/`paths:`; passo 1 `checar-aditiva.sh`, passo 2 subida extraída + `ensaiar-migration.sh`. O `checar-aditiva.test.sh` (sem banco) roda junto do teste do `migrar.sh` (passo do TP-0008).
7. `migrar.sh` (TP-0008, edição mínima): acrescentar `migration` à lista de jobs exigidos verdes antes do `db push` (G-12, ADR-011 §4.2) + caso no `migrar.test.sh`.
8. `backend/README.md`: o que o job faz, como reproduzir (`bash backend/operacao/deploy/ensaiar-migration.sh --base origin/main`), formato da justificativa com os casos (a) e (b).

PENDENTE: `supabase db diff` gera `drop policy` + `create policy` ao mudar uma política, e `drop function` ao acrescentar "parâmetro novo com default" (que a TASK 1.3 chama de aditivo; sem o drop da assinatura antiga a chamada fica ambígua). Pela G-12 literal esses casos exigem (a) ou (b), e não existe fase *expand* para eles. Liberar quando o mesmo objeto é recriado na mesma migration (política de mesmo nome; função de mesmo nome cuja nova assinatura só acrescenta parâmetros com default), ou cada um vira exceção no Log? É mudança de checagem: precisa do Gestor.
PENDENTE: o job `migration` só protege a `main` se entrar nos checks obrigatórios configurados no TP-0030 ([U], painel/`gh api`). Quem acrescenta, e quando (esta tarefa não é [U])? Relacionada à PENDENTE de TP-0030 sobre os nomes de check.

Não fazer: credencial ou `supabase link`/`db push` no CI (G-06); `git checkout`/`stash` na árvore local (usar `git archive` em pasta temporária); fixture em `migrations/` ou em `tests/`; ID de tarefa em nome de arquivo ou de migration. Fora do aceite (só registrar como sugestão em `## 4`): falhar quando uma migration já existente na `main` é editada.

## 2. Plano de teste
- `checar-aditiva.test.sh` (repositório git temporário com `<base>` e um commit "PR"; sem banco): migration nova só com `create`/`add column … default` → passa; com `drop table` sem justificativa → falha; `drop` só em comentário → passa; `rename column` e `alter column … type` → falham; `alter type … add value` → passa; justificativa (a) com expand de 31 dias (commit com `GIT_COMMITTER_DATE`) → passa; expand de 10 dias → falha; expand inexistente na base → falha; (b) com linha de log na base citando G-12 e o arquivo → passa; mesma linha só no PR → falha; validade vencida → falha; justificativa sem (a) nem (b) → falha.
- `ensaiar-migration.test.sh` [BD] (Supabase local): pasta temporária com o `backend/supabase` do HEAD + `backend/supabase/ensaio/not_null_sem_default.sql` copiada para `migrations/` com timestamp no futuro (`alter table app.lancamento add column ensaio_obrigatoria text not null;` em `begin/commit`) → código ≠ 0 e log com "violates not-null" depois do seed de volume (prova do aceite); `ensaio/coluna_com_default.sql` → código 0.
- CI: no PR desta tarefa, `migration` verde (sem migration nova e com a fixture positiva num commit do branch) e vermelho com a fixture `not null` num commit do branch, depois retirado pelo próprio executor; links das duas execuções em `## 4`.
- `migrar.test.sh`: run verde sem o job `migration` → aborta antes do dump.
- Comandos: `bash backend/operacao/deploy/testes/checar-aditiva.test.sh`, `bash backend/operacao/deploy/testes/ensaiar-migration.test.sh`, `bash backend/operacao/deploy/testes/migrar.test.sh`, `shellcheck backend/operacao/deploy/*.sh`.

## 4. Resultado da execução
**Feito**
- `backend/operacao/deploy/checar-aditiva.sh <base>`: migrations novas via `git diff -z --diff-filter=A <base>...HEAD`; remove comentários (perl), detecta `drop`, `rename` e `alter table … alter [column] x [set data] type`; exige `<nome>.justificativa.md` ao lado com `Fase expand:` (existe na base, entrou há >= 30 dias, `git log --diff-filter=A --format=%cs`) ou `Exceção: <data>` (linha do Log lido de `git show <base>:.md/GUARDRAILS.md`, com G-12, nome da migration e validade permanente/não vencida). Nome de migration nunca é avaliado como código.
- `backend/operacao/deploy/ensaiar-migration.sh --base <ref> [--workdir-pr backend]`: trava de host, `git archive <base> backend/supabase` em pasta temporária, `db reset --workdir <tmp>/backend`, `carregar.sh` da base, `migration up --local --workdir <pr>`.
- Extraída a trava de host de `carregar.sh` para `backend/operacao/comum/host-local.sh` (`exigir_host_local`), usada por `carregar.sh` e pelo ensaio (o ensaio copia o `host-local.sh` para a pasta temporária da base, porque `carregar.sh` o carrega relativo a `backend/`).
- `ci.yml`: job `migration` (checkout `fetch-depth: 0`, passo de base de comparação, checagem aditiva, `preparar-pnpm`, `pnpm local:ci`, ensaio); passo de testes de deploy da `base` agora roda também `migrar-job-migration.test.sh` e `checar-aditiva.test.sh`. Permissions, SHAs e demais jobs intactos.
- `migrar.sh`: `JOBS_EXIGIDOS=(base migration)`; `simular.sh` (padrão de `SIM_GH_JOBS`) inclui o job `migration` verde para o caminho feliz de `migrar.test.sh`.
- `backend/README.md`: seção "CI de migration" (o que faz, como reproduzir, formato da justificativa (a)/(b)).
- Ajuste no teste pré-escrito `ensaiar-migration.test.sh`: o Postgres responde `column "…" contains null values` ao `add column … not null` sobre linhas existentes (não "violates not-null"); o teste aceita as duas mensagens.
