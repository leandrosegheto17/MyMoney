**Camada:** `src/dados/comandos/lancarDespesa.ts` e `src/dados/fila/` (`armazem.ts`, `fila.ts`, `tipos.ts`) (SDD §2; único lugar com IndexedDB, G-08).
**Referência visual:** não se aplica.

1. Dependências `idb-keyval` e `fake-indexeddb` (dev), se ainda não estiverem: o TP-0076 roda em paralelo. Reler `package.json` antes de editar; registrar em `## 4`. uuid por `crypto.randomUUID()` (sem dependência).
2. `dados/comandos/lancarDespesa.ts`: `lancarDespesa(args)` → `rpc('lancar_despesa', args)`; erro → lança `traduzirErro(e)`. Única chamada à RPC (a fila usa esta função).
3. `dados/fila/tipos.ts`: `ItemFila = { id, dono, args: { p_id, p_valor_centavos, p_categoria_id, p_forma_id, p_parcelas, p_data, p_descricao }, exibicao: { categoria_nome, escopo, forma_nome }, criadoEm, situacao: 'aguardando' | 'falhou', motivo?: CodigoErro | 'desconhecido' }`. `p_data` **obrigatório** no item (a T03 propõe "hoje" na confirmação; sem isso o servidor usaria o dia do envio, errado). `exibicao` é o que a T23 e o rodapé da T04 mostram sem rede (TP-0104, TP-0108).
   RESOLVIDO (Coordenador, 2026-10-09): o campo `dono` guarda o `user.id` da sessão (1:1 com o membro, ADR-008) e é ele que se compara no envio (atende o ADR-007 §7). O aceite do TP-0077 no TASK.md passou de `membro_id` para "o `user.id` da sessão". `exibicao` ganha também `escopo` (a T23 mostra o selo Casa/Eu). O formato do item é o de `.md/mockup/respostas/fila-offline.json`, que o modo de comparação usa para semear a fila (TP-0089); manter os dois iguais (teste de tipo com `satisfies ItemFila[]` sobre esse JSON).
4. `dados/fila/armazem.ts`: `createStore('mymoney-fila', 'itens')`; chave = `id`; ordem por `criadoEm` (+ `id` no empate).
5. `dados/fila/fila.ts` (exportado como `fila`, nome citado na TASK 1.5):
   - `enfileirar(args sem p_id, exibicao)`: sessão atual obrigatória; gera `id`, monta o item `aguardando` e **grava antes** de qualquer envio; devolve o item. Não envia (quem dispara o envio é a T03 e os gatilhos do TP-0078).
   - `esvaziar()`: trava única em memória (segunda chamada durante um envio devolve a mesma promessa) e `navigator.locks.request('mymoney-fila', …)` quando existir (duas abas). Pega só itens `aguardando` com `dono` = `user.id` atual, em ordem, um por vez. Sucesso → remove e emite `{ tipo: 'enviado', item, resposta }` (a T23 mostra "Enviado: 1ª parcela em 10/11"); `rede`/`indisponivel` → para a rodada, item intacto; erro de autenticação (401/JWT) → para, item intacto (renovação é do TP-0078); `regra` → `falhou` com `motivo = codigo` e segue para o próximo (interpretação: falha não bloqueia os demais; registrar); `desconhecido` → `falhou` com `'desconhecido'` (nada some, nada repete para sempre).
   - `listar()` (todos os itens do dono atual), `descartar(id, { confirmado: true })` (sem `confirmado === true` lança e não apaga; o diálogo é da T23), `assinar(cb) → cancelar` (mudanças e eventos de envio, base do contador do TP-0078).
   - Item de outro `dono`: nunca enviado, nunca apagado, nunca listado para o membro atual.
6. Ordem TDD: tipos → testes da fila (seção 2) → `armazem` → `fila` → comando.

Não fazer: gatilhos `online`/`visibilitychange`/30 s e renovação de sessão (TP-0078); "Tentar agora"/"Corrigir" (TP-0108 acrescenta); fila para receita ou outras escritas (ADR-007 §1, G-17); calcular data de parcela (só vem na resposta, R-UX-02); `sair()` nunca chama a fila.

## 2. Plano de teste
Vitest, `import 'fake-indexeddb/auto'` no arquivo, `lancarDespesa` simulado por `vi.mock` (e um teste do comando com `fetch` simulado), sessão simulada em `obterSessao`:
- Gravação antes do envio: `enfileirar` + `fetch` que nunca resolve → o item já está no IndexedDB com `dono`, `p_id` uuid v4 e `p_data`.
- Ordem: 3 itens → chamadas na ordem de `criadoEm`, a 2ª só começa depois da 1ª resolver (contador de chamadas em curso ≤ 1).
- Rede no 2º → 1º removido, 2º e 3º intactos e `aguardando`; nova rodada envia os dois.
- Regra (`erro-registro-invalido.json`) → item `falhou` com `motivo 'registro_invalido'`, os seguintes enviados; 503 → item intacto.
- Resposta perdida: servidor grava e a resposta falha com `TypeError` → item fica; reenvio usa o **mesmo** `p_id` e recebe `ja_existia: true` → removido; o simulador registra 1 lançamento só.
- Outro membro: itens de `dono` A, sessão de B → nada enviado, nada removido, `listar()` vazio para B; volta A → enviados.
- `descartar` sem confirmação lança e mantém; com `{ confirmado: true }` remove.
- Trava: duas chamadas simultâneas de `esvaziar` → cada item enviado uma vez.
- `assinar` recebe `enviado` com a resposta (`lancar-despesa-credito.json`).
- Comando: `pnpm --filter @mymoney/web test -- src/dados/fila src/dados/comandos/lancarDespesa`; `pnpm --filter @mymoney/web typecheck`.
