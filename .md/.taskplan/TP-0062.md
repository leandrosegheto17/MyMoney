1. TDD: pgTAP (seção 2) primeiro, depois o caso de `testes-api`.
2. Assinatura: `api.lancar_despesa(p_id uuid, p_valor_centavos bigint, p_categoria_id uuid, p_forma_id uuid, p_parcelas integer default 1, p_data date default null, p_descricao text default null) returns jsonb`; `security invoker`, `set search_path = ''`, primeira linha `v_membro := app.membro_atual()` (nulo → `registro_invalido`, usuário sem membro, G-16).
3. Idempotência (ADR-003 §6, G-17), antes de validar: se `app.lancamento` com `id = p_id` e `dono_id = v_membro` existe → devolver a resposta montada a partir do que está gravado, com `ja_existia: true`, sem regravar nem comparar parâmetros. Se existe visível mas de outro dono (conjunta de A vista por B) → `registro_invalido`. Se não visível pela RLS, o `insert` estoura `unique_violation`: capturar e levantar `registro_invalido` (mesmo erro de "não existe", G-05). Corrida do mesmo membro (dois envios simultâneos): no `unique_violation`, reler; se for seu, devolver o anterior.
4. Validação: `p_valor_centavos` nulo ou ≤ 0 → `valor_invalido`. Categoria: `select` em `app.categoria` sob RLS com `tipo = 'despesa'`; não achou → `registro_invalido`; arquivada → `categoria_arquivada`. Forma: `select` em `app.forma_pagamento` com `dono_id = v_membro`; não achou → `registro_invalido`; arquivada → `forma_arquivada`. Pix/Débito com `p_parcelas` ≠ 1 → `valor_invalido` (interpretação registrada). `v_data := coalesce(p_data, app.hoje())`. Descrição: `nullif(btrim(p_descricao), '')`.
   RESOLVIDO (Coordenador, 2026-10-09): `categoria_arquivada` e `forma_arquivada` (e `conta_arquivada` para conta, usado pela receita), só alcançáveis em registro visível ao membro, então não revelam dado do outro (G-05). Os códigos já nascem na lista completa do TP-0019. Registrado no SDD §2 ("Códigos de erro"). Testes fixam o código.
5. Gravação (uma transação, a da própria chamada): `app.lancamento` (`id = p_id`, `lar_id = app.lar_atual()`, `tipo = 'despesa'`, `escopo` = escopo da categoria (RN-01), `dono_id = v_membro` (RN-05: quem lança é o pagador), `categoria_id`, `descricao`, `valor_total_centavos`, `num_parcelas`); `app.lancamento_pagamento` (`forma_pagamento_id`, `data_operacao = v_data`; Pix/Débito: `conta_id` = conta da forma no momento, para o saldo do TP-0064 (interpretação registrada); Crédito: `dia_vencimento_aplicado` = dia da forma, ADR-005 §4); `app.parcela`: Pix/Débito 1 parcela (`numero 1`, total, `data = v_data`); Crédito: `insert ... select from app.gerar_parcelas(v_data, dia, p_parcelas, p_valor_centavos)`. `data_ajustada = false`. Colunas de RLS da parcela (`lar_id`/`dono_id`/escopo) conforme o TP-0051.
6. Resposta (forma do JSON, D-03, superconjunto do aceite): `{id, escopo, categoria (nome), valor_total_centavos, num_parcelas, primeira_parcela_data, ja_existia}`. Interpretação: no reenvio todos os campos são iguais aos da primeira resposta, exceto `ja_existia = true` (registrar em `## 4`).
7. `revoke execute ... from public, anon; grant execute ... to authenticated` (conferir o padrão do TP-0003). `supabase db diff -f api_lancar_despesa`, `begin; … commit;`, `pnpm local:resetar`, `pnpm contrato:gerar` e commitar o `banco.ts` regenerado. Atualizar `backend/README.md` só se surgir comando novo.

Não fazer: `security definer`; recalcular parcela fora de `app.gerar_parcelas`; ler `auth.uid()` direto; mensagem de erro em texto livre; caso de fila offline (é do frontend, TP-0077).
