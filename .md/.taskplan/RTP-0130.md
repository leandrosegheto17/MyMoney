# RTP-0130 — pagar_ocorrencia: limitar a data do pagamento a uma faixa plausível

Reserva: Livre
Devoluções: 1
Origem: DevSecOps de TP-0132 (baixa). `api.pagar_ocorrencia` usa `p_data` sem validar faixa (`coalesce(p_data, app.hoje())`): o cliente só oferece "hoje" como padrão, mas uma chamada direta grava data da operação arbitrária (ex.: ano 9999), distorcendo saldo/extrato do próprio pagador (sem vazamento entre membros). G-07: o servidor é quem valida.

## 1. Plano de execução
Em `backend/supabase/schemas/api/funcoes/pagar_ocorrencia.sql`, recusar `v_data` fora de uma faixa plausível (limite superior perto de `app.hoje()`, inferior fixo) com a exceção de regra já usada pelo projeto; gerar a migração; teste de API com data absurda.

## 2. Plano de teste
`npx vitest run testes-api/casos/pagar-ocorrencia.test.ts` (variáveis do `.env.example`): data 9999-12-31 e 1900-01-01 recusadas; data de hoje aceita.

## 4. Resultado da execução
- `api.pagar_ocorrencia` recusa `v_data` fora de 2000-01-01..`app.hoje()+30` com `valor_invalido` (exceção já existente no contrato e no cliente; sem erro novo, sem mudança de assinatura, então sem `contrato:gerar`). Migration aplicada ao banco local com `supabase migration up`, sem reset.
- Arquivos: `backend/supabase/schemas/api/funcoes/pagar_ocorrencia.sql`, `backend/supabase/migrations/20261014120000_pagar_ocorrencia_limita_data.sql` (novo), `backend/testes-api/casos/pagar-ocorrencia.test.ts`.
- Testes: `npx vitest run testes-api/casos/pagar-ocorrencia.test.ts` (env local): 7 passando (9999-12-31 e 1900-01-01 recusadas; hoje aceita; reenvio idempotente). `pnpm contrato:verificar`: em dia. Sem pgTAP novo (cobertura via teste de API, conforme o plano).
- Checklist de convenções: sem duplicação, sem IDs em comentários, comentário do cabeçalho atualizado.
- Risco: o limite superior de 30 dias é uma escolha minha (o plano diz "perto de hoje"); ajustar se o SDD definir outro.

## 3. Plano de validação de segurança
Confirmar que a recusa não vaza dado de outro membro e que o reenvio idempotente continua funcionando.

## 5. Resultado do QA
Veredito: DEVOLVIDA (1 crítico, 2 não críticos).

Conferido OK:
- Migration `20261014120000_...` posterior a todas as demais, aplicada no banco local (consta em `migration list --local`) e idêntica à fonte declarativa (diff do corpo da função: sem drift). `pnpm contrato:verificar`: "contrato em dia".
- Suíte de API `casos/pagar-ocorrencia.test.ts` (env local): 7 passando; 9999-12-31 e 1900-01-01 recusadas, hoje aceita, reenvio idempotente.
- Erro é `valor_invalido` (código estável do contrato), sem eco da entrada.
- Convenções: sem duplicação nem ID em comentário. Só o comentário de cabeçalho ficou com linha longa (>100 col) por ter sido acrescentado sem reflow (cosmético, junto do reparo abaixo).

Achado CRÍTICO (devolve ao executor): regressão em pgTAP. `pnpm exec supabase test db --workdir backend` termina em FAIL: `supabase/tests/formas/gasto_cartao_fixa.sql` testes 14-19 (6 falhas), todos os demais 106 arquivos passam. Esse teste chama `api.pagar_ocorrencia` com `p_data` '2026-12-05' (virada de ano) e '2027-01-20' (cartão dia 31), que com hoje=2026-10-14 passam do limite hoje+30 e agora levantam `valor_invalido`. A mudança da tarefa quebrou a suíte existente e o executor não rodou o pgTAP. Reparo: o teste deve fixar `app.hoje()` (como `fixas/pagar_ocorrencia.sql` já faz) ou usar datas dentro da faixa, e vale buscar outros testes (API/e2e/pgTAP) que paguem com data futura. Sobre pgTAP novo: o aceite diz só "teste de API", então não exijo arquivo pgTAP novo; o caso de API cobre a regra (ver RTP-0136 para o resto).

Limite superior hoje+30 (item 4): razoável. `app.hoje()` já é a data em São Paulo, então a comparação é por data local sem risco de fuso; o cliente envia por padrão hoje (`hojeEmSaoPaulo`). A "data do pagamento" é a data da operação (efetivada), não o vencimento (que fica na parcela), então pagar adiantado uma fixa de meses à frente não exige data futura distante: a fixa de dezembro pode ser paga hoje. Os 30 dias deixam folga para agendar/fuso. Não é bloqueio; apenas registrar que é decisão de produto não escrita no SDD.

Achado não crítico 1 (RTP-0136): `CampoData` de `FolhaPagarFixa` não tem `min`/`max`, então o cliente deixa escolher data que o servidor recusa. Achado não crítico 2 (mesma RTP-0136): a recusa cai no genérico "Valor inválido. Confira e tente de novo" (texto de valor, não de data), pouco coerente na folha.

Resumo para o relatório: DEVOLVIDA — API 7/7 e contrato/migration OK, mas pgTAP regrediu (formas/gasto_cartao_fixa.sql 14-19, datas futuras agora recusadas); 1 crítico, 2 não críticos (RTP-0136: min/max e mensagem de data na folha).
