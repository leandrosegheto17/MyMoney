**Referência visual:** não se aplica.

1. TDD: pgTAP de estrutura, restrições e RLS primeiro (seção 2).
2. `despesa_fixa.sql`: `id uuid pk default gen_random_uuid()`, `lar_id uuid not null default app.lar_atual() → app.lar`, `descricao text not null check (btrim(descricao) <> '')`, `categoria_id uuid not null`, `tipo text not null default 'despesa' check (tipo = 'despesa')` e `escopo text not null default 'conjunto' check (escopo = 'conjunto')` só para o FK composto `(categoria_id, tipo, escopo) → app.categoria(id, tipo, escopo)` **sem** `on delete` (no action: o `excluir_categoria` do TP-0060 traduz o FK em `categoria_em_uso`), `valor_previsto_centavos bigint not null check (> 0)`, `dia_vencimento smallint not null check (between 1 and 31)`, `inicio date not null default app.inicio_mes(app.hoje())` com `check (inicio = date_trunc('month', inicio)::date)`, `encerrada_em date null`, `criado_em`. Sem `dono_id`: a fixa é do lar (SDD §5).
3. `ocorrencia_fixa.sql`: `id`, `lar_id` (default como acima), `despesa_fixa_id uuid not null → app.despesa_fixa` (no action; não há exclusão de fixa no contrato), `mes date not null check (mes = date_trunc('month', mes)::date)`, `vencimento date not null` com `check (date_trunc('month', vencimento) = mes)`, `valor_previsto_centavos bigint not null check (> 0)` (cópia do modelo na geração, RN-15 "editável no pagamento"), `lancamento_id uuid null unique → app.lancamento(id) on delete set null`, `criado_em`. `unique (despesa_fixa_id, mes)` (RN-15, índice do SDD §5) e índice `ocorrencia_fixa(lar_id, mes)` (leitura do mês, TP-0124/TP-0127).
   - `on delete set null`: excluir o lançamento da fixa paga (TP-0100, que deixou o vínculo para cá) volta a ocorrência a pendente, como o "desfazer" (CA-12.3). Interpretação registrada em `## 4`. A ação de FK ignora a RLS (B excluindo a conjunta de A): provar no pgTAP.
4. RLS `enable` + `force` nas 2, políticas por comando com `lar_id = app.lar_atual()` (`using` e `with check`), nunca lendo `app.membro`. Grants a `authenticated`: `despesa_fixa` `select, insert, update` (sem `delete`); `ocorrencia_fixa` `select, insert, update, delete` (o `encerrar`, TP-0123, apaga pendentes). Nada a `anon`.
5. `seeds/06-fixas.sql` (dados com `lar_id` explícito, o seed roda sem JWT): os 7 modelos de `respostas/despesas-fixas.json` (`…0701`–`…0707`, categorias `…0403`–`…0405`, `inicio = '2026-01-01'`) e as 7 ocorrências de outubro/2026 de `respostas/ocorrencias-mes.json` (`…0801`–`…0807`, vencimentos do JSON). As 4 pagas (Luz e Gás e Diarista por Ana, Água por Leandro) ganham neste seed o lançamento conjunto do pagador (1 parcela no vencimento com o valor pago do JSON, `lancamento_pagamento` com a forma Pix do pagador dos seeds 03 e `data_operacao` no vencimento), ids novos na faixa `…05xx`/`…06xx` sem colidir com o seed 05; registrar em `## 4`.
   Ponto de atenção: esses 4 lançamentos mudam os totais de outubro do seed. Rodar os pgTAP e `testes-api` que leem o seed (totais, lista do mês, resumo) e, se algum contar linhas do seed, registrar em `## 4` em vez de mexer no teste de outra tarefa sem necessidade.
6. `supabase db diff -f despesas_fixas`; políticas e grants que o diff não capturar à mão; `begin; … commit;`; `pnpm local:resetar`.

Não fazer: `app.garantir_ocorrencias` (TP-0120), views e funções `api.*` (TP-0121 a TP-0125); coluna de situação (é derivação, TP-0124); `lancamento.ocorrencia_id`; ID de tarefa na migration.
