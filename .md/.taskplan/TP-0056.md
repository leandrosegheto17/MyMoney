1. TDD: `tests/cadastros/salvar_forma.sql` primeiro.
2. `api.salvar_forma(p_id uuid, p_nome text, p_tipo text, p_conta_id uuid default null, p_dia_vencimento smallint default null) returns uuid`, `security invoker`, `search_path = ''`. Membro por `app.membro_atual()` (nulo → `registro_invalido`). Sem parâmetro de preferida: é o `api.definir_preferida` (TP-0058); a T18 chama os dois (TP-0069).
3. Validação, nesta ordem, antes de gravar (os `check` do TP-0049 ficam como rede de segurança):
   - `p_id` nulo, nome vazio (`btrim`) ou `p_tipo` fora de `pix|debito|credito` (valores de `TipoForma`, TP-0020) → `valor_invalido`;
   - Pix/Débito: `p_conta_id` nulo → `valor_invalido`; `p_dia_vencimento` é ignorado (gravar nulo);
   - Crédito: dia nulo ou fora de 1..31 → `valor_invalido` (CA-03.2a); conta opcional;
   - conta informada: `select arquivada from app.conta where id = p_conta_id` (a RLS só mostra as do membro); não achou (inexistente ou de B) → `registro_invalido`; arquivada → `valor_invalido`, **só** quando a conta muda (editar uma forma cuja conta foi arquivada depois continua possível; registrar em `## 4`).
4. Edição: ler a forma do membro (`where id = p_id and dono_id = v_membro`); se existe e `tipo <> p_tipo` → `valor_invalido` (R-UX-06). Senão `update` de nome, conta e dia; senão `insert` pelo padrão do TP-0054.
5. CA-03.2b: mudar `dia_vencimento` só altera a forma. Nenhuma parcela, nenhum `lancamento_pagamento.dia_vencimento_aplicado` é tocado (a data já gravada é a verdade, ADR-005). Não escrever nada além de `app.forma_pagamento`.
6. Grants (`revoke … public, anon; grant … authenticated`); `db diff -f api_salvar_forma`; `begin; … commit;`; `pnpm local:resetar`; `pnpm contrato:gerar`.

Não fazer: recalcular parcelas; mexer em `preferida`/`arquivada`; `security definer`; traduzir `check_violation` em texto livre.
