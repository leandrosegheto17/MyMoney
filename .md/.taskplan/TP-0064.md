## 1. Plano de execução
**Reaproveitamento:** USAR `app.conta` (`saldo_inicial_centavos`) e `app.movimento_conta` (`tipo`, `sentido`, `valor_centavos`, `data`; índice `(conta_id, data)`) do TP-0048; `app.forma_pagamento.tipo` do TP-0049; `app.lancamento` (`tipo`), `app.lancamento_pagamento` (`conta_id`, `forma_pagamento_id`, `data_operacao`, RLS só do pagador) e `app.parcela` do TP-0051; `app.hoje()` do TP-0004 (única fonte de "hoje"); privilégios padrão de função do TP-0003 (não repetir grants); ajudante pgTAP "executar como membro" do TP-0013. O `api.lancar_despesa` (TP-0062) grava `lancamento_pagamento.conta_id` = conta da forma para Pix/Débito e nulo no Crédito: é por essa coluna que a despesa se liga à conta. Esta função é o módulo único de saldo: `api.contas` (TP-0065), `api.ajustar_saldo` (TP-0066), `resumo_mes` (TP-0087) e TP-0158 vão USÁ-la; nenhum outro lugar recalcula saldo.
**Camada:** banco, `backend/supabase/schemas/app/funcoes/saldo_conta.sql` (função interna `app.*`, não exposta; SDD §2 "Camadas do banco"); pgTAP em `backend/supabase/tests/contas/`.
**Referência visual:** não se aplica.

1. TDD: `tests/contas/saldo_conta.sql` primeiro (seção 2), ver falhar.
2. `app.saldo_conta(p_conta_id uuid, p_ate date default app.hoje()) returns bigint`, `language sql stable security invoker set search_path = ''`. O parâmetro `p_ate` com default segue o padrão de `app.hoje(p_instante)` (TP-0004): permite testar a borda de D-12 sem mexer no relógio; os consumidores chamam só `saldo_conta(id)`. Interpretação registrada em `## 4`.
3. Corpo (nomes qualificados), sobre a conta visível (`from app.conta c where c.id = p_conta_id`; conta de outro ou inexistente → `null`, a RLS do TP-0048 filtra):
   - `c.saldo_inicial_centavos`;
   - `+ Σ` lançamentos `tipo = 'receita'` com `lp.conta_id = c.id` e `lp.data_operacao <= p_ate`;
   - `− Σ` lançamentos `tipo = 'despesa'` com `lp.conta_id = c.id`, forma `tipo in ('pix','debito')` (filtro explícito, defensivo contra Crédito com conta) e `lp.data_operacao <= p_ate`;
   - valor de cada lançamento = `Σ parcela.valor_centavos` do lançamento (não ler `valor_total_centavos`, espírito da G-11; Pix/Débito/receita/fixa à vista têm 1 parcela, mas a data da parcela de fixa é o vencimento, por isso o filtro de data é sempre `data_operacao`, ADR-005 §6);
   - `± Σ movimento_conta` da conta com `data <= p_ate` (`entrada` soma, `saida` subtrai; vale para ajuste, aporte, retirada e pagamento de cartão, RN-12).
   - `coalesce(…, 0)` em cada soma; resultado `bigint`.
4. `supabase db diff -f saldo_conta`; `pnpm local:resetar`; `pnpm contrato:gerar` sem diff (schema `api` não muda).

Não fazer: coluna ou cache de saldo; somar parcela por competência (`parcela.data`); considerar `forma_pagamento.conta_id` atual em vez de `lp.conta_id` (a troca de conta da forma não reescreve o histórico); `security definer`; ID de tarefa no SQL ou na migration.

## 2. Plano de teste
pgTAP `backend/supabase/tests/contas/saldo_conta.sql`, como A (JWT), dados criados na transação por `insert` direto nas tabelas (RLS de dono permite; `lancar_despesa`/`lancar_receita` não são dependência):
- Só saldo inicial 1000,00 → `100000`; conta com saldo inicial 0 e nada → `0`.
- Receita de 500,00 com `data_operacao = hoje` → `+50000`.
- Despesa Pix 120,00 e Débito 30,00 ligadas à conta → `−15000`; despesa Pix ligada a **outra** conta de A → sem efeito.
- Crédito 3x de 600,00 (parcelas no mês corrente e seguintes, `lp.conta_id` nulo, forma com `conta_id` de pagamento = esta conta) → sem efeito (RN-13).
- `movimento_conta`: ajuste entrada 12,30 → `+1230`; aporte saída 200,00 → `−20000`; retirada entrada; pagamento de cartão saída → cada um com o sinal certo.
- D-12: receita e movimento com data `hoje + 1` → fora; `app.saldo_conta(id, hoje + 1)` → dentro. Fixa paga por Pix com parcela no vencimento futuro e `data_operacao = hoje` → entra.
- Isolamento: como B, `app.saldo_conta(<conta de A>)` → `null` (igual a id inexistente).
- Privilégio: `anon` sem `execute`.
