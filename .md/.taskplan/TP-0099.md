3. Regras do ADR-003 §3, na ordem: (a) `search_path = ''`; (b) 1ª linha `v_membro := app.membro_atual()` (lê `auth.uid()`), nulo → `registro_invalido`; (c) `select … from app.lancamento where id = p_id for update` + `app.permissoes_edicao(p_id)` (que já recusa individual alheia com `registro_invalido`); (d) só devolve campos não privados; (e) casos de isolamento próprios (seção 2).
4. Para cada parâmetro que difere do gravado, exigir a permissão correspondente, senão `sem_permissao` (registro visível, não revela nada): `descricao`, `valor`, `data` (no crédito, `data` é a data da compra, `lancamento_pagamento.data_operacao`), `forma`, `parcelas`; categoria nova com outro escopo → `troca_escopo`, mesmo escopo → `categoria_mesmo_escopo`.
5. Validação explícita (a RLS não vale aqui): valor ≤ 0 → `valor_invalido`; categoria nova: mesmo `tipo`, `lar_id = app.lar_atual()`, `escopo = 'conjunto' or dono_id = v_membro`, não arquivada, senão `registro_invalido`; forma nova: `dono_id = v_membro` (só o pagador chega aqui), ativa; Pix/Débito com N ≠ 1 e N fora de 1..24 → `valor_invalido` (mesmas regras do TP-0062; código de arquivada: mesma PENDENTE de TP-0062).
6. Recálculo (CA-08.5a: valor, N, data da compra, forma ou categoria): dia = `dia_vencimento_aplicado` congelado; forma nova de crédito → dia da forma nova. `v_novas := app.calcular_parcelas(...)`. Se existe `data_ajustada` e `not p_confirmar_descarte` → `raise exception 'confirmar_descarte_ajustes'` **antes** de qualquer escrita. Gravar preservando os ids: `update` das parcelas com `numero <= N novo` (valor, data, `data_ajustada = false`), `delete` das sobrando, `insert` das novas.
7. Gravação: `lancamento` (categoria e escopo no mesmo `update`, RN-07; parcelas seguem pelo cascade), `lancamento_pagamento` (forma, `conta_id` da forma nova se Pix/Débito, nulo no Crédito; `data_operacao`; `dia_vencimento_aplicado`), e sempre `alterado_por = v_membro`, `alterado_em = now()`.
8. Resposta mínima `{id, escopo, num_parcelas, alterado_em}`; a tela relê `api.lancamento` (TP-0102). NUNCA chamar `api.lancamento` ou montar `pagamento` aqui: dentro do DEFINER a RLS não filtraria a parte privada para B.
9. PENDENTE: editar **receita** (a T04 abre a T05 também para receita): trocar a conta de destino entra? Sugestão: parâmetro aditivo `p_conta_id uuid default null`, só para o dono, receita com 1 parcela na data. Até a resposta, receita aceita valor, data, descrição e categoria de receita.
10. Grants: `revoke … from public, anon; grant execute … to authenticated`. `supabase db diff -f api_editar_lancamento`, `pnpm local:resetar`, `pnpm contrato:gerar`. Conferir que o dono da função ignora a RLS (pgTAP: B editando a data de uma conjunta Pix de A altera `data_operacao` de A); se não ignorar, parar e registrar.

## 3. Plano de validação de segurança
- G-03 / ADR-003 §3: única DEFINER de `api`; conferir no diff as 5 regras uma a uma, nomes qualificados, `search_path = ''`.
- Toda leitura feita sem RLS tem o filtro explícito de lar/escopo/dono (categoria, forma, lançamento); revisar cada SELECT.
- RN-04: a resposta não contém campo privado; nenhuma chamada a leitura que dependa de RLS dentro da função.
- RN-06/RN-07/CA-08.3: comparar "o que mudou" × permissão antes de gravar; erro antes de qualquer escrita (inclusive no descarte).
- G-05: individual alheia = inexistente (`registro_invalido`). G-10: `bigint`, datas `date`. Revisão obrigatória do Validador (ADR-003, consequências).
