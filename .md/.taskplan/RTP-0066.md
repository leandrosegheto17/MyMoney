# RTP-0066 — pedirRedefinicao: não engolir erro de limite de taxa

Reserva: Livre
Status-local: Concluída · aguarda QA
ID no TASK.md: RTP-0066 · Lote: Refatoração Lote-5 · Agente: executor · Chapéu: Frontend · Est: 1h · Dep: TP-0025 · Status no TASK.md: Pendente
Reqs: QA de TP-0025; UX T01; plano TP-0025 passo 5 · Aceite: `pedirRedefinicao` só devolve resultado neutro para usuário inexistente; rede, indisponível e limite de taxa (429/`over_email_send_rate_limit`) lançam `ErroDados`; teste cobre os três

## 1. Plano de execução
Origem: QA de TP-0025 (achado não crítico). `frontend/web/src/dados/sessao.ts` `pedirRedefinicao` descarta todo erro que não seja `rede`/`indisponivel`, inclusive limite de taxa: a tela mostra "enviado" sem e-mail enviado. O plano pedia neutralidade só para "usuário não existe". Ajustar a tradução (`erros.ts`) para distinguir limite de taxa (status 429 ou code `over_email_send_rate_limit`) e relançá-lo; manter o neutro para os demais erros de usuário. Se faltar código de contrato para limite de taxa, levar ao coordenador antes de criar.

## 2. Plano de teste
`sessao.test.ts`: 200 e usuário inexistente devolvem o mesmo resultado; rede, 503 e 429 rejeitam com `ErroDados`. `pnpm exec vitest run src/dados/sessao.test.ts`.

## 3. Plano de validação de segurança
Conferir que a resposta para usuário inexistente continua idêntica à de sucesso (G-05, sem enumeração de e-mail) e que nenhum texto do servidor chega à tela.

## 4. Resultado da execução
**Feito:** `traduzirErro` passou a traduzir limite de taxa do Auth (HTTP 429 ou code `over_email_send_rate_limit`/`over_request_rate_limit`/`over_sms_send_rate_limit`) como `{ tipo: 'indisponivel' }`. Como `pedirRedefinicao` já relançava `rede`/`indisponivel`, o 429 deixa de ser engolido; usuário inexistente (404 `user_not_found`) segue neutro (idêntico ao 200). Não foi criado código novo no contrato `@mymoney/contrato/erros` (o plano manda levar ao coordenador antes): usada a variante genérica `indisponivel`, a tela mostra a mensagem de indisponibilidade existente. Atualizado o comentário de `pedirRedefinicao`.

**Arquivos:** `frontend/web/src/dados/erros.ts`, `frontend/web/src/dados/sessao.ts` (só comentário), `frontend/web/src/dados/erros.test.ts`, `frontend/web/src/dados/sessao.test.ts`.

**Casos de teste:** sessao: 200 e usuário inexistente iguais (já existia); rede; 503 -> indisponivel; 429 sem code -> indisponivel; 429 `over_email_send_rate_limit` -> indisponivel. erros: 429, `over_email_send_rate_limit`, `over_request_rate_limit` -> indisponivel.

**Comandos (em frontend/web):** `pnpm exec vitest run src/dados/sessao.test.ts src/dados/erros.test.ts` -> 2 arquivos, 25 testes passando; `pnpm exec tsc --noEmit` e `pnpm exec eslint src/dados` sem saída (limpos). Não há script `lint` no package.

**Conferência de convenções:** sem cópia de código, sem IDs de tarefa em código/comentário, arquivos pequenos, sem import novo.

**Riscos / para o coordenador:** (1) 429 em `entrar` agora também vira `indisponivel` (antes `desconhecido`); coerente, mas a tela mostra "indisponível" em vez de erro genérico. (2) Se desejado texto específico de "muitas tentativas", é preciso novo código no contrato (aditivo) e rótulo em `rotulos/` — decisão do coordenador. (3) Não verifiquei o texto do UX-SPEC T01b para indisponibilidade; a tela usa o rótulo existente de `indisponivel`.
