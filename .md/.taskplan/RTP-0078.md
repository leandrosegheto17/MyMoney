# RTP-0078 — Cache do aparelho: descartar registro de outro usuário

Reserva: Livre

## 1. Plano de execução
Origem: DevSecOps do TP-0076 (severidade baixa). Se a sessão acaba sem `sair()` (expiração, sair offline), o cache do membro A fica no IndexedDB; membro B no mesmo aparelho não o lê pelo app, mas os dados persistem em disco até B abrir com rede. Em `lerCache`, quando `registro.usuarioId` difere de `usuarioId`, apagar o registro (só o store `mymoney-cache`, nunca a fila) e devolver `undefined`.

## 2. Plano de teste
Em `cacheDadosLancamento.test.ts`: salvar como A, ler como B → `undefined` e depois ler como A também `undefined`; item em `mymoney-fila` continua.

## 4. Resultado da execução

- Feito: `lerCache` apaga (`del`, só no store `mymoney-cache`) o registro de outro usuário e devolve `undefined`. Teste novo: salvar como A, ler B e A -> `undefined`; item em `mymoney-fila` permanece.
- Arquivos alterados: `frontend/web/src/dados/local/cacheDadosLancamento.ts`, `frontend/web/src/dados/local/cacheDadosLancamento.test.ts` (nenhum fora de frontend/).
- Testes: `npx vitest run src/dados/local/cacheDadosLancamento.test.ts src/dados/sessao.cache.test.ts src/dados/consultas/dadosLancamento.test.ts` -> 3 arquivos, 18 passando, 0 falhando.
- Checklist de convenções: sem duplicação, sem IDs de tarefa em comentários, comentário de `lerCache` atualizado, arquivos pequenos, sem import fora das fronteiras; não é tarefa de tela.
- Riscos: nenhum relevante; a leitura agora tem efeito colateral de escrita (apagamento).

## 3. Plano de validação de segurança
Confirmar que só o store `mymoney-cache` é limpo (G-17) e que dados de A não sobrevivem à leitura de B.
