## 1. Plano de execução
**Reaproveitamento:** USAR o pacote `backend/contrato` do TP-0019 (`package.json`, `tsconfig.json`, `src/erros.ts` com `CodigoErro`). Acrescentar entradas em `exports`; não recriar o pacote. Os JSON de `.md/mockup/respostas/` são a fonte (D-03) e não são copiados para o pacote: o teste os lê de lá.
**Camada:** `@mymoney/contrato` (`backend/contrato/src/respostas/` e `src/enums.ts`). Só tipos, sem lógica (SDD §2).
**Referência visual:** não se aplica.

1. `src/enums.ts` com as uniões compartilhadas por vários recursos: `Escopo` (`conjunto`|`individual`), `TipoForma` (`pix`|`debito`|`credito`, SDD §5), `TipoLancamento` (`despesa`|`receita`), `SituacaoOrcamento` (`dentro`|`atencao`|`estourado`), `SituacaoOcorrencia` (`pendente`|`atrasada`|`paga`), `TipoMovimentoMeta` (`aporte`|`retirada`). Base do `rotulos/` (TP-0038). Valores conferidos contra todos os JSON (nenhum valor fora da união).
2. Um arquivo por recurso, nome em kebab: `contexto.ts`, `dados-lancamento.ts`, `resumo-mes.ts`, `lancamentos-mes.ts`, `lancamento.ts`, `ocorrencias-mes.ts`, `orcamento-mes.ts`, `movimentos-meta.ts`, `locais-guardados.ts`, `lancar-despesa.ts`, `contas.ts`, `formas-pagamento.ts`, `categorias.ts`, `despesas-fixas.ts`, `metas.ts`. Linhas de view exportadas como `Linha<Recurso>` (a resposta é `Linha[]`). Subtipos repetidos (ex.: `{id, nome}` de conta/categoria, item por categoria do resumo) declarados uma vez e importados, não redeclarados.
3. Forma = a do JSON, não a tabela do SDD (D-03): `contexto` tem `membro.email` e `hoje`; `resumo_mes` tem `pendentes_previstos_centavos`, `fixas_total`, `minha_parte_por_categoria`; `dados_lancamento` tem `conta_receita_padrao_id`; `orcamento_mes` tem `sem_orcamento`.
4. `lancamento.ts`: `pagamento` (forma, conta, data da operação) é **opcional** (`pagamento?:`), nunca `| null`: para o outro membro vem ausente (SDD §2, RF-08; compare `lancamento-pagador.json` × `lancamento-outro-membro.json`).
5. Datas `string` com JSDoc do formato: `YYYY-MM-DD` (ADR-004); `mes_corrente` é `YYYY-MM-01`; `metas[].prazo` é `AAAA-MM` (`meta-carro.json`). Centavos `number` inteiro.
6. `package.json`: `exports` `"./respostas/*": "./src/respostas/*.ts"` e `"./enums": "./src/enums.ts"`. Sem `index.ts`.
7. Ponto de atenção: quando as views existirem, o `banco.ts` gerado terá `Views[...]['Row']` com tudo `| null` e `Json` no lugar de objetos aninhados (ex.: `formas_pagamento.conta`). O frontend usa os tipos daqui; as tarefas de view garantem a mesma forma via `mesmaForma` (TASK 1.4).

## 2. Plano de teste
- Armadilha: `import x from '*.json'` alarga literais para `string`, e `satisfies Escopo` não compila mesmo com JSON certo. Por isso o teste **gera** TS a partir do texto do JSON: `test/respostas.test.ts` (Vitest) lê cada JSON, monta em memória `import type {T} from '../src/respostas/<r>'; const _ = <texto do JSON> satisfies T;` e compila com a API do `typescript` (`noEmit`, opções do `tsconfig`), falhando com os diagnósticos. O literal com `satisfies` também pega campo a mais no JSON (excess property check).
- Tabela única JSON → tipo cobrindo os 37 arquivos: 34 mapeados (vazios e variantes inclusos: `*-vazio`, `contexto-ana`, `dados-lancamento-sem-formas`, `conta-nubank`, `forma-xp`, `categoria-mercado`, `despesa-fixa`, `meta-carro`, `meta-detalhe`, `lancamento-*`, `lancar-despesa-credito`); `erro-registro-invalido.json` checado contra `{ message: CodigoErro }` de `erros.ts`; `auth-usuario.json` e `erro-servico.json` excluídos com motivo (Auth/gateway, fora do schema `api`). Meta-caso: arquivo novo em `respostas/` sem linha na tabela falha.
- Caso negativo: JSON com `escopo: "casa"` em memória deve falhar (prova que o teste detecta).
- `pnpm --filter @mymoney/contrato typecheck` e `test` verdes.
