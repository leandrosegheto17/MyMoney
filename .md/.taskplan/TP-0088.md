# TP-0088 — Seed de volume de 2 anos e medição do desempenho [BD]

Reserva: Livre

Reqs: RNF-03; RT-08; ADR-011 §4.2 · Aceite: Script que gera cerca de 6.000 parcelas para os 2 membros num arquivo de seed opcional (fora do `local:resetar` padrão); com ele, `resumo_mes` e `lancamentos_mes` ficam abaixo de 500 ms no Supabase local e o `explain` usa os índices; resultado registrado no `backend/README.md`

## 1. Plano de execução
**Reaproveitamento:** USAR `api.lancar_despesa` (TP-0062) para gerar as despesas, assim as parcelas saem de `app.gerar_parcelas` (TP-0061) e nenhuma regra de parcela/data de cartão é reescrita no seed (CONVENCOES regra 1); membros, contas, formas e categorias dos seeds `01-acesso.sql` a `04-categorias.sql` (TP-0014, TP-0048, TP-0049, TP-0050/0052); a forma de "executar como membro" (`role authenticated` + `request.jwt.claims`) do ajudante pgTAP do TP-0013 (USAR o ajudante se estiver num schema carregável fora do pgTAP; senão, as mesmas 2 `set_config`); `api.resumo_mes` (TP-0087); índices `parcela(lar_id, data)`/`(dono_id, data)` (TP-0051). O script de carga é o que o TP-0109 vai reaproveitar no CI.
**Camada:** banco, `backend/supabase/volume/` (fora de `seeds/`, porque o `sql_paths = ["./seeds/*.sql"]` do TP-0002 carregaria tudo em `seeds/` no `db reset`): `volume-2-anos.sql` (gerador), `carregar.sh`, `medir.sql`. Todo SQL continua em `backend/supabase/` (G-08).
**Referência visual:** não se aplica.

1. `volume-2-anos.sql` (determinístico, sem `random()`): para cada um dos 24 meses até o mês de `app.hoje()` e para cada membro, executar como o membro e chamar `api.lancar_despesa` com id `md5('volume-' || n)::uuid` (reexecução idempotente, G-17), valor/categoria/forma/data escolhidos por aritmética modular sobre `n`: ~80% à vista (Pix/Débito), ~20% no Crédito de 2 a 12x, mistura conjunta/individual e variável/fixa. Ana só tem 1 forma no seed 03: o arquivo cria para ela, por `api.salvar_forma` (TP-0056), um Débito e um Crédito com ids fixos da faixa `…03xx` (registrar em `## 4`). Receitas mensais de cada membro: `api.lancar_receita` só nasce no TP-0115 (Lote 23); até lá, inserir direto (lançamento + pagamento + 1 parcela, sem regra a repetir) e registrar. Ajustar a quantidade para que o total de `app.parcela` fique entre 5.500 e 6.500; o script termina com `raise exception` se ficar fora.
2. `carregar.sh`: recusa URL que não seja `localhost`/`127.0.0.1` (G-06), lê a URL do banco de `supabase status -o env` e roda o arquivo com `psql` (se o `psql` não estiver na máquina, `docker exec` no container do banco; registrar). Script de raiz `pnpm local:volume` (depois de `pnpm local:resetar`).
3. `medir.sql`: como A, 1 aquecimento + 5 execuções de `select api.resumo_mes(<mês corrente>)` e de um mês com crédito futuro, mediana do tempo (`\timing`); `explain (analyze, buffers)` com `auto_explain` (`log_nested_statements = on`, `client_min_messages = log`) para ver os planos de dentro das funções, conferindo `Index Scan`/`Bitmap Index Scan` em `parcela_lar_id_data`/`parcela_dono_id_data`. Se o `LOAD 'auto_explain'` não for permitido ao usuário local, `explain analyze` da consulta de `app.parcelas_mes` (TP-0085) e registrar. Script `pnpm local:medir`.
4. `backend/README.md`: seção "Seed de volume e desempenho" com os comandos, contagem de parcelas, tempos (mediana) e o trecho do plano que mostra o índice; data e máquina.
5. PENDENTE: o aceite mede também `lancamentos_mes`, mas `api.lancamentos_mes` só nasce no TP-0096 (Lote 19, depois deste lote) e não é dependência. Proposta: esta tarefa mede `resumo_mes` e deixa no `medir.sql` o bloco de `lancamentos_mes` comentado como pendente; o TP-0096 acrescenta a medição dele (< 500 ms) e atualiza o README. Alternativa: mover o TP-0088 para depois do TP-0096.

Não fazer: colocar o arquivo em `seeds/` (entraria no `local:resetar` e no reset do CI); inserir parcelas à mão para despesa (duplica RN-14); dado real; qualquer conexão fora do local; índice novo sem medir antes (se o tempo passar de 500 ms, registrar e escalar ao Coordenador, SDD §6 "dívida de materialização"); ID de tarefa em arquivo ou nome.

## 2. Plano de teste
- Execução de ponta a ponta: `pnpm local:resetar && pnpm local:volume && pnpm local:medir`; critério: contagem de parcelas entre 5.500 e 6.500, dividida entre os 2 membros e entre conjunto/individual; mediana de `resumo_mes` < 500 ms; plano com índice de `parcela`.
- Idempotência: rodar `pnpm local:volume` duas vezes → mesma contagem.
- Sanidade com os testes já existentes: `pnpm exec supabase test db --workdir backend` continua verde depois do `local:resetar` (o volume não entra no padrão); `pnpm --filter @mymoney/testes-api test -- resumo-mes` contra o banco com volume dá `mesmaForma` verde.
- Trava de host: `carregar.sh` com URL não local → sai com erro antes de conectar (teste com `bash` simples, como o `simular.sh` do TP-0008, se existir).
- [BD] exclusivo.

### Testes unitários já escritos
- **Arquivos:** `backend/supabase/volume/testes/carregar.test.sh` (bash puro, comandos simulados no `PATH`).
- **Interfaces fixadas pelo teste:** `carregar.sh` lê `DB_URL` de `supabase status -o env` (direto ou via `pnpm exec supabase`), roda sem argumentos e sai ≠ 0 sem chamar `psql`/`docker` se o host não for exatamente `localhost`/`127.0.0.1` ou se a URL vier vazia.
- **Desvios do plano:** não usa `comum/testes/simular.sh` (interface não definida); simulações próprias no arquivo.
- **Fora do unitário:** carga ponta a ponta, contagem de parcelas, idempotência, medição < 500 ms e `explain` (manual/[BD]).

## 3. Plano de validação de segurança
- G-06 / G-14 / ADR-011: o volume só roda no Supabase local; trava de host no `carregar.sh`; nenhum caminho para a produção (`db push` não aplica seed; arquivo fora de `seeds/`).
- Dados fictícios, sem nome ou valor real (ADR-011 "seeds sem dado real"). G-15: sem `service_role`; o script usa a URL local do `supabase status`.
- A carga passa pelas funções `api.*` como cada membro (RLS e regras valem); conferir no diff que não há `security definer`, `set role postgres` para despesas nem `disable row level security`.
